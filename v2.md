# mew v2 — live steering, reliable navigation, visible cursor

**Context:** `mew` v1 (see original `README.md`/spec) is functional through Step 11 scaffolding. Manual testing surfaced three real gaps. This file is the fix plan. Same format as before: **N.1 = implementation session, N.2 = review/testing session**, done separately, by you, with your own eyes. Don't move to N+1.1 until N.2 is genuinely checked off.

Each step is scoped to be one sitting — not a multi-day slog, not a five-minute stub.

---

## Why these bugs happen (read once before starting)

This isn't `mew`-specific sloppiness. All three are named, studied failure modes in the LLM-browser-agent literature as of 2026:

- **Going silent mid-task** is the default shape of a naive ReAct loop: one `await` chain, LLM call → tool call → LLM call, with no channel for anything else to get in. Every serious agent harness (Magentic-UI's "co-tasking," LangGraph's `interrupt()/resume`) solves it the same way — an explicit pause/resume state machine plus a side-channel the loop polls between steps, not a redesign of the LLM prompt.
- **"Open X" failing while "search then open X" works** is called out by name in the BrowserArena benchmark paper (2026) as one of only three consistent cross-model failure categories, alongside captcha handling and popup dismissal. Models are unreliable at guessing bare domains and either hallucinate a wrong URL or refuse. The fix lives in the tool layer, not the prompt.
- **Visible cursor** has an almost identical open issue in Google's own `chrome-devtools-mcp` project (issue #2401, filed this year) with a working reference implementation: inject a small script via `Page.addScriptToEvaluateOnNewDocument` (`page.evaluate_on_new_document()` in chromiumoxide) so a CSS-only ghost cursor survives navigations, driven by whatever x/y you already compute for `Input.dispatchMouseEvent`. Low difficulty, well-precedented, zero effect on real automation when off.

## Step 12.1 — Agent state machine: implementation

Before anything else, give the agent loop an explicit lifecycle instead of an opaque `while` loop. Every later step depends on this existing first.

- [x] In `mew-agent`, define an enum `SessionState { Running, Paused, Stopped, Done, Failed }` and a `SessionHandle` struct that wraps it behind an `Arc<Mutex<..>>` (or `tokio::sync::watch` if you're comfortable with it — either works, don't overthink which).
- [x] Add explicit transition methods: `pause()`, `resume()`, `stop(reason: String)`. Enforce the state machine in code — e.g. `stop()` is terminal, no transitions out of `Stopped`/`Done`/`Failed`. Panics or silently-ignored calls on an invalid transition are both wrong; return a typed error instead.
- [x] Add a single `checkpoint()` async method the main loop will `.await` between every tool call (not yet wired to anything — that's 12.1's next bullet and Step 13). For now it just checks current state and, if `Paused`, blocks until `resume()` is called.
- [x] Wire `checkpoint()` into the existing Step 6 ReAct loop: call it once after receiving the model's tool call, before executing it. Nothing else changes yet — you're not adding the chat channel in this step, just the machinery it will plug into.
- [x] Log every state transition (with timestamp) to the existing session transcript from Step 10.

## Step 13.1 — Live chat channel into the running agent: implementation

This is the core fix for "can't talk to him while he's using Chrome."

- [x] In `mew-cli`, create an `mpsc::channel::<UserMessage>` (bounded, capacity ~32 is fine) at startup. The sender half goes to whatever reads your terminal/stdin (or your future UI input) input; the receiver half is moved into the agent loop.
- [x] In `mew-agent`'s main loop, change the shape from a plain `await` chain to a `tokio::select!` between: (a) waiting on `checkpoint()`/the current tool-call future, and (b) `rx.recv()` on the new channel. **Be careful here** — `select!` inside a `loop` has a known footgun (it can silently starve one branch if not structured right); the safer shape is: run one loop iteration (one full LLM-call → tool-call round trip) as a cancel-safe unit, and only check the channel *between* iterations via a non-blocking `try_recv()` at the same point `checkpoint()` already runs — don't try to interrupt a tool call that's mid-flight (e.g., mid-click). Interrupt between steps, not inside one.
- [x] When a message arrives on the channel: append it to the running conversation history as a new `role: user` message (don't clear or restart history), log it to the transcript, and let the next LLM call see it alongside the latest snapshot/diff. No task restart, no state wipe.
- [x] Add a plain-text way to actually send messages while the CLI is mid-run — simplest version: a second thread reading stdin line-by-line and pushing to the sender, printed prompt like `(you can type here anytime) >`.
- [x] Make sure typing a message doesn't require the agent to be paused — the default behavior should be "steer while running" (per Magentic-UI's model), with `pause()` from Step 12 reserved for when you explicitly want it to freeze and wait (e.g., before handing you manual control of the browser).

## Step 14.1 — URL resolution layer ("open X" fix): implementation

Fixes the specific bug: bare site names failing while "search then click" succeeds.

- [ ] In `mew-agent` (or a new small `mew-nav` module if you prefer separation), add a resolution function that runs **before** the model's `navigate(url)` tool call ever reaches `mew-cdp`: given a bare word/phrase like `"instagram"`, check a small local map first (`instagram → https://www.instagram.com`, `gmail → https://mail.google.com`, `youtube → https://www.youtube.com`, etc. — seed it with the 15-20 sites you actually use, from the original scope-lock step).
- [ ] If not in the map: try constructing `https://{x}.com` (strip spaces/punctuation first) and attempt a real navigation with a short timeout (e.g. 3-4s) purely to check it resolves to a real page (not a DNS error / not a search-engine "no results" redirect). If it loads, use it.
- [ ] If that also fails: fall back to `https://www.google.com/search?q={x}` automatically — this is the exact "use google and open X" path that already works, just triggered automatically instead of requiring you to say it.
- [ ] Make this resolution step transparent in the transcript: log which path was taken (map hit / direct-guess hit / search fallback) so you can see why a given site did what it did.
- [ ] This resolution function is what the model's `navigate` tool call actually goes through — the model still says `navigate("instagram")`, but your code (not the model's guess) decides the final URL.

## Step 14.2 — URL resolution layer: review & testing

- [ ] Test with a real site NOT in your map but with a predictable `.com` (e.g. some site you don't use often) — confirm it correctly guesses and lands there, and the transcript shows the "direct-guess" path.
- [ ] Test with a deliberately nonsense/ambiguous phrase (e.g. "that shopping site" or a misspelled name) — confirm it falls through cleanly to the Google search fallback rather than erroring out or hanging.

- [ ] Check the 3-4s timeout on the direct-guess path actually fires and falls through — don't let a slow-loading real site get misclassified as "failed" and sent to search instead; if you see false negatives here, loosen the timeout slightly and retest.

**Done when:** your exact original failing phrasing now works, and you've confirmed via transcript logs which of the three resolution paths fired for at least 3 different real test cases.

## Step 15.1 — Task completeness check (avoid silent partial-completion): implementation

Targets a general agent failure pattern: the agent believing a task is done when it isn't. (Research note: one 2026 paper on GUI agents found 86%+ of "false completion" cases happen because the agent calls `finish()` without checking real on-screen evidence — this is a generic, well-known failure mode across the field, not something specific to any one site or task.)

- [ ] When the task involves multiple similar sub-actions (e.g. "do X for each of these N things"), have the agent (via system prompt instruction) explicitly enumerate the sub-items as a checklist at the start, and have your code — not the model's memory — track which are marked done, in a simple `Vec<SubTask>` with a `done: bool` per item.
- [ ] Before allowing `finish()` to actually end the session, add a code-level gate: if any tracked subtask is still `false`, force one more `snapshot()` and require the model to explicitly justify each incomplete item (skipped on purpose vs. actually failed) rather than letting `finish()` short-circuit silently.
- [ ] Require the "done" evidence to come from a fresh snapshot/diff taken right before marking a subtask complete — not from the model's own claim in text. E.g. for a repeated action, confirm the diff shows the expected new element/state change each time, not just once at the end.
- [ ] Log a clear per-subtask summary at the end of every session: what was attempted, what evidence confirmed it, what didn't complete and why.

## Step 15.2 — Task completeness check: review & testing

- [ ] Give it a multi-item task (3+ similar repeated actions) and deliberately make one of them impossible partway through (e.g. an item that doesn't exist) — confirm the final summary correctly reports partial success with the specific failed item named, instead of a blanket "done."
- [ ] Give it the same kind of task with everything actually achievable and confirm it doesn't get stuck over-verifying forever — this should add one honest check, not turn every task into an infinite loop of double-checking.
- [ ] Read the per-subtask summary from a real run yourself and confirm it's genuinely accurate against what you watched happen on screen — not the model's optimistic gloss.
- [ ] Confirm the "fresh snapshot as evidence" rule is actually being followed — grep the transcript and check a `snapshot()`/diff call genuinely happens before each subtask is marked done, not just once at the very end covering all of them.

**Done when:** you've seen a deliberately-broken multi-item task get accurately reported as partial (not falsely "done"), and confirmed the evidence-before-completion rule is really being enforced in the transcript, not just declared.

## Step 16.1 — Visible cursor overlay: implementation

Precedented, low-difficulty, cosmetic-only feature — does not touch real automation logic.

- [ ] Write a small injected script (plain JS/CSS) that renders a fixed-position `div` styled as a cursor (simple circle/arrow, CSS `position: fixed`, high `z-index`, `pointer-events: none` so it never interferes with real page interaction) and expose a JS function on `window` to move it, e.g. `window.__mewCursor.moveTo(x, y)`.
- [ ] Register it via `page.evaluate_on_new_document(script)` (chromiumoxide's direct equivalent of Playwright's `addInitScript`) so it's re-injected automatically on every navigation, not just the first page load.
- [ ] In `mew-cdp`, wherever you already compute x/y before calling `Input.dispatchMouseEvent` (click, hover, drag), add a call to `window.__mewCursor.moveTo(x, y)` via `page.evaluate()` immediately before the real dispatch, with a small delay (100-200ms) so the movement is visibly perceptible rather than instant-teleport.
- [ ] Gate the whole feature behind a `visible_cursor: bool` field in `config.yaml`, defaulting to `false` — when off, zero extra calls, zero latency change, code path fully skipped.
- [ ] Add a brief "ripple" or color-flash CSS animation at the moment of an actual click, so clicks are visually distinguishable from plain hovers/moves.

## Step 16.2 — Visible cursor overlay: review & testing

- [ ] Enable the flag, run a normal task, and watch the actual window yourself — confirm the ghost cursor visibly slides to each click target before the click happens, not teleporting or lagging behind the real action.
- [ ] Navigate to a second page mid-session and confirm the cursor still appears (proves `evaluate_on_new_document` is really re-injecting per navigation, not just showing up once by luck on the first page).
- [ ] Confirm real clicks still land correctly with the overlay on — the `pointer-events: none` should mean the fake cursor never blocks or redirects an actual click. Test on a page with a tightly-packed clickable element to be sure.
- [ ] Turn the flag off, re-run the same task, and confirm zero visible cursor and — check logs/timing — no measurable slowdown or extra CDP calls being made.
- [ ] Check it doesn't interfere with the Step 9 stealth binary — run once with stealth + visible cursor together and confirm both still work (the injected script itself shouldn't trip any bot-detection differently than before, since it never touches `navigator.*` properties).

**Done when:** you've watched the cursor move and click on screen across a real multi-page session, confirmed it survives navigation, confirmed real clicks are unaffected, and confirmed the off-switch is a true no-op.

## Step 17.1 — Site-specific pacing guard (recommended, not mandatory): implementation

Research note, since you asked for enhancement ideas beyond the mandatory list: repeated identical actions in quick succession (e.g. sending several messages back-to-back) is a documented trigger for platform-side bot detection independent of anything wrong with your agent — this is a real risk on any site with anti-automation systems, not just one. Worth a lightweight guard regardless of which site you're on.

- [ ] Add a simple per-action-type cooldown/jitter setting in `config.yaml` (e.g. `min_delay_ms` / `max_delay_ms` for repeated identical actions like consecutive sends/clicks of the same kind), defaulting to a modest random delay (e.g. 800-2500ms) between repeats of the *same* action type in a loop.
- [ ] Apply it only to repeated same-type actions in a tight loop (e.g. "do this N times") — not to every single action globally, which would just make the agent sluggish for no reason.
- [ ] Log when the pacing delay is applied so you can see it's real in the transcript, not just configured and ignored.

## Step 17.2 — Site-specific pacing guard: review & testing

- [ ] Run a repeated-action task and confirm via transcript timestamps that consecutive same-type actions are genuinely spaced out by roughly the configured range, not fired back-to-back despite the setting.
- [ ] Confirm a single one-off action (not part of a repeated loop) isn't needlessly delayed — the guard should be scoped correctly, not blanket-applied.
- [ ] Set the delay range to something absurdly low temporarily and confirm the code path still works (just faster) — proves the delay is real logic, not a hardcoded sleep that happens to look right at default settings.

**Done when:** you've confirmed via real timestamps that repeated actions are actually paced, and that one-off actions aren't needlessly slowed down.

## Reference notes for this file

- State-machine + side-channel pattern: same shape as Magentic-UI's "co-tasking" (user interrupts without losing agent state) and LangGraph's `interrupt()/Command(resume=...)`.
- `select!`-in-a-loop caution: prefer checking the channel via `try_recv()` at a clean checkpoint between whole iterations, rather than racing `select!` against a tool call that's mid-flight — cancelling a half-finished click/type is a real correctness risk, not just a style preference.
- URL-resolution-before-model-guess is the standard fix for the "direct navigation" failure category identified across models in the BrowserArena benchmark (2026).
- False-completion mitigation (evidence-before-`finish()`) mirrors the "Completeness Verifier" pattern from recent GUI-agent robustness research — the core idea is simply: the LLM decides what to do, your code decides whether "done" is actually true.
- Visible cursor: same problem and same fix as `chrome-devtools-mcp` issue #2401 — inject via `Page.addScriptToEvaluateOnNewDocument` (chromiumoxide: `page.evaluate_on_new_document()`), keep `pointer-events: none`, gate behind a flag, no effect on real input dispatch.
